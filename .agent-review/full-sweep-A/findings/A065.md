## Bug Summary
`service.test.ts` L11-13 imports fixtures (`makeFormats`, `makeFs`,
`makeDbForImport`, `makeFileSync`, `baseConfig`, `makeDb as makeRagDb`,
`makeRag`, `makeEmbed`) directly from sibling `*.test.ts` files
(`dispatch.test.ts`, `indexer.test.ts`, `importer.test.ts`). This is a
test-infrastructure smell: (1) Vitest will load and execute the sibling
files' `describe` blocks as a side effect of the import — inflating
runtime and risking shared-state leakage if a sibling ever adds module
scope; (2) deleting or renaming any sibling silently breaks
`service.test.ts`; (3) the test files now have a public API surface that
isn't versioned or documented.

## Reproduction
- Test file: `apps/rishi-electron/src/renderer/src/services/book-import/service.test.ts` lines `11-13`
- Failing condition: rename `makeRag` in `indexer.test.ts` (a refactor
  that should be local to one test file) and `service.test.ts` will fail
  with `TypeError: ... is not a function`, with no compile-time hint
  from the importing file.
- How to run: `pnpm --filter rishi-electron test src/renderer/src/services/book-import/service.test.ts`

## Tester Analysis
Belongs in `test-infra-backlog.md`. The fix is to extract these helpers
into `src/renderer/src/services/book-import/__fixtures__/` (or a
`test-helpers.ts` co-located but NOT `*.test.ts`) so that:
- Vitest discovery does not execute fixture files as test suites.
- The helper API is a deliberate export, decoupled from any one spec.
- Sibling-test changes don't cause cross-spec collateral failure.
The pilot guidance in §3 calls out exactly this pattern.
