## Bug Summary
`tutorialStore.test.ts` `beforeEach` (L5-14) hand-crafts a literal
`{tourActive, tourStep, tourCompleted, tourPaused, hintsShown}` reset
object via `useTutorialStore.setState(...)` instead of calling the
production reset `resetTour()` (tutorialStore.ts:137-151) or
`setState(getInitialState(), true)`. This is the exact anti-pattern
plan-stores-A flagged for pdfStore (now fixed by pilot Q06). If a new
state field is added to `TutorialState` (e.g. `tourVariant`,
`lastShownAt`, telemetry counters), the fixture will silently leave it
at the value bled in from a previous test, masking regressions in any
function that reads the new field.

## Tester Analysis
Production code already exposes a complete reset path: `resetTour()` at
tutorialStore.ts:137-151 zeroes all five state fields AND clears
`HINTS_SEEN_KEY` localStorage AND calls `persistTourCompleted(false)`.
The test fixture bypasses all of that: it manually rebuilds the state
literal and only clears localStorage at L6 with a blanket
`localStorage.clear()`. This means:

1. State drift: new fields added later are not reset.
2. Persisted state drift: the test relies on `localStorage.clear()`
   wiping everything, but a real reset path would also exercise the
   `persistTourCompleted(false)` branch (L77-88) which is currently
   untested in the reset fixture.
3. Divergence between test reset and production reset: future audits
   will not catch a regression where `resetTour()` stops clearing a
   field that the fixture also forgot.

Use either `useTutorialStore.getState().resetTour()` (preferred — also
exercises the persist branch) or
`useTutorialStore.setState(useTutorialStore.getInitialState(), true)`
if the goal is to avoid persistence side effects.
