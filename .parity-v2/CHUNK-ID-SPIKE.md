# CHUNK-ID-SPIKE — T-P0.2

**TL;DR / Verdict:** **D — DEEPER-INVESTIGATION-NEEDED** (and on the surface,
**B — DIVERGENT-ALIGN-SHARED**, with caveats).

The two files named `indexer.ts` (electron renderer + shared) do **not** generate
chunk IDs themselves. They both consume a `PageDataInsertable[]` whose `id` field
is stamped upstream. Chunk-ID generation lives in **two separate code paths**:

| Path | Where chunk IDs are minted | Formula |
| --- | --- | --- |
| Electron renderer (PDF pipeline) | `packages/shared/src/indexing/index-program.ts:81-82` (`chunkId(pageNumber, bookId, index)`) | Positional integer: `pageNumber*1_000_000 + bookId*10_000 + index` |
| Mobile RAG chunker (PDF/EPUB/MOBI/AZW3/DJVU) | `apps/mobile/lib/rag/chunker.ts:72-74` (`chunkIdFor(bookId, chunkText)`) | Content-addressable: `stringToNumberID(\`${bookId}\|${chunkText}\`).toString()` |

Same input → **different IDs**. The two formulae are structurally incompatible
(positional vs. content-hash; numeric `bookId` vs. string-UUID `bookId`). This
is a real divergence, already acknowledged in `.parity/BATCH-2A-NOTES.md`
(lines 71–97) as a parked deviation awaiting Batch 2B / parity-v2.

## 1. Electron indexer logic (file:line walk-through)

`apps/rishi-electron/src/renderer/src/services/book-import/indexer.ts`

- L27–32 `indexBook(deps, bookId, pageDataOpt, progressEmit)` — entry. Skips
  fully if `chunksExist && vectorsExist` (L33–37).
- L40–53 Resolves `pageData`:
  - L41 caller-provided `pageDataOpt` wins.
  - L43 else if chunks already in DB → `db.getAllPageDataByBookId(bookId)` — IDs
    come from the DB row (set at chunk-write time, upstream).
  - L51 else `pageData = []` (electron has no inline chunk-generation path here
    — chunks are generated by the format-specific PDF/EPUB pipeline before the
    indexer is ever called).
- L58–63 If chunks missing: maps to `ChunkDataInsertable` and saves via
  `db.savePageDataMany`. Critically, **the `id` field is passed through
  verbatim** (`id: p.id`) — no minting here.
- L72–82 Embed + save vectors batched by `embedBatchSize`. `id` is again
  pass-through to `r.metadata.id`.

**Where do those IDs originate on electron?** `chunkId` from
`packages/shared/src/indexing/index-program.ts` (L81-82):

```ts
export const chunkId = (pageNumber: number, bookId: number, index: number): number =>
  pageNumber * 1_000_000 + bookId * 10_000 + index
```

This is invoked at `index-program.ts:103` inside `processPage` as
`chunks.map((data, index) => ({ id: chunkId(pageNumber, deps.bookId, index), ... }))`.
That pipeline is what fills the rows that the indexer above then reads.

Per the BATCH-2A notes:
- `bookId` is **numeric** on electron (sqlite integer PK).
- ID is **positional**: same `(pageNumber, bookId, paragraphIndex)` → same id,
  regardless of text content. Re-chunking with different paragraph splits ⇒
  same id but different text (no collision detection, but `INSERT OR IGNORE`
  on the chunk_data table keeps the first write).
- The HNSW vector label is the same int — formula MUST stay stable.

## 2. Shared indexer logic (file:line walk-through)

`packages/shared/src/book-import/indexer.ts`

- L35–47 `indexBook<BookId, Book, BookInsertable>` — generic over BookId.
  Same short-circuit (`chunksExist && vectorsExist`).
- L52–66 `pageData` resolution mirrors electron with one **mobile-only**
  branch: `else if (filePath && format) { generated = await
  deps.embed.generateChunks(...) }` (L57-63). The IDs on those generated rows
  come from whatever `EmbedPort.generateChunks` returns.
- L69–74 If chunks missing → `db.savePageDataMany(pageData)`. IDs pass through.
- L79–98 Embed + save vectors. `id` passes through to vector metadata.

**Where do those IDs originate on mobile?**
`apps/mobile/lib/book-import/adapters.ts:425-435` wires `generateChunks` to
`runEmbedPipeline` (L352-421), which calls
`apps/mobile/lib/rag/chunker.ts:347 getChunks(filePath, format, bookId)`.
`getChunks` runs format-specific extraction (EPUB/PDF/MOBI/AZW3/DJVU) and
funnels every result through `chunkSections` (L243-255):

```ts
function chunkSections(sections, bookId, ...) {
  const raw = chunkText(sections, maxChunkSize, overlap)
  return raw.map((c) => ({ ...c, id: chunkIdFor(bookId, c.text), bookId }))
}
```

and `chunkIdFor` (chunker.ts:72-74):

```ts
function chunkIdFor(bookId: string, chunkText: string): string {
  return stringToNumberID(`${bookId}|${chunkText}`).toString()
}
```

`stringToNumberID` is the classic Java-style `h = h*31 + c` djb-ish hash
(`packages/shared/src/lib/stringToNumberID.ts:8-15`):

```ts
let hash = 0
for (let i = 0; i < str.length; i++) {
  const char = str.charCodeAt(i)
  hash = ((hash << 5) - hash + char) | 0
}
return Math.abs(hash)
```

The mobile path then stuffs that **string-typed** id into the chunk row and
synthesises a positional-looking `PageDataInsertable` only as a sentinel for
the shared indexer (`adapters.ts:415-420`: `id: idx` — the integer **index**,
not the chunk id, because mobile already wrote the real row via
`insertChunkWithVector(chunk.id, ...)` at L385-393).

## 3. Side-by-side comparison (chunk-ID generation steps)

| Step | Electron (PDF) | Mobile (PDF/EPUB/MOBI/AZW3/DJVU) |
| --- | --- | --- |
| Input identity | `(pageNumber: number, bookId: number, index: number)` | `(bookId: string, chunkText: string)` |
| Normalisation | None — pure positional | None — raw text concatenated with `\|` separator |
| Algorithm | `pageNumber*1_000_000 + bookId*10_000 + index` | djb-ish 32-bit folded hash via `stringToNumberID` |
| Output type | `number` (signed-int range, positional, sparse) | `string` (decimal repr of `Math.abs(h)`, dense, ~31-bit) |
| Salt / seed | none | none |
| Effect of text edits | id is **invariant** to text changes | id **changes** with text |
| Effect of pagination changes | id changes (page #) | id is invariant to pagination if chunk text is unchanged |
| Format coverage | PDF only (`index-program.ts`) — EPUB on electron uses a **different** legacy pipeline (`indexBook` consumers stamp `id: p.id` from upstream DB rows, originally minted in the legacy `process_epub.ts`, see indexer.ts:19 comment) | All five formats funnel through `chunkSections` → same formula |

**Functional differences:**

1. **Type mismatch.** Numbers (electron) vs decimal strings (mobile). The
   SQLite column on electron is INTEGER; on mobile it's TEXT (see
   `insertChunkWithVector` invocation, `adapters.ts:385-393`).
2. **bookId type mismatch.** Electron requires numeric `bookId`; mobile uses
   string UUIDs. Cannot trivially feed mobile UUIDs into electron's formula
   (would need a string→int map).
3. **Semantics.** Electron formula is positional → a re-paginated PDF gets
   *different* IDs; mobile formula is content-addressable → a re-paginated PDF
   keeps IDs *as long as chunk text is byte-identical*.
4. **Collision profile.** Electron formula is collision-free over
   `(pageNumber<10⁶, bookId<10⁴, index<10⁴)`. Mobile formula is a 31-bit hash
   → birthday-collisions at ~46k chunks; the `${bookId}|` prefix scopes
   collisions per-book but two chunks of the same book with identical
   trimmed text get the same id (probably fine; chunker already de-dups
   empties).

For the same `(bookId, pageNumber, index)` triple **the two formulae produce
different numeric values**, so the same PDF processed on both sides yields
disjoint chunk-ID sets. They are not parity-equivalent.

## 5. Verdict: D (with B as the recommended resolution)

- The two paths are **functionally divergent today**. (Not A.)
- The deeper investigation has two open questions:
  1. **What does "parity" mean for chunk IDs, exactly?** Is the goal that
     the *same row in sync replicates byte-identically across devices* (in
     which case IDs must be equal end-to-end and we need cross-platform
     content addressing), or is it merely that *each side can independently
     dedup re-imports* (in which case stable-per-side is enough and sync uses
     a different key)? Per `.parity/BATCH-2A-NOTES.md` line 86-87, the
     stated goal is **cross-platform dedup**, which requires identical IDs.
  2. **Which side owns the canonical formula?** Per spec preference
     (BATCH-2A-NOTES L88-93), content-addressable from shared is preferred,
     i.e. **electron should adopt mobile's content-hash formula**. But this
     is a destructive migration for electron: existing HNSW labels and
     chunk_data rows are keyed on the positional integer; a switch breaks
     every already-indexed book on every existing install unless a
     migration is shipped (re-index on first launch).
- **Provisional recommendation: B — DIVERGENT-ALIGN-SHARED**
  (i.e. electron migrates to the shared content-addressable formula), but
  only after T-P0.2 explicitly answers (a) the migration plan for existing
  electron installs and (b) the numeric-vs-string column type for
  `chunk_data.id` (mobile's TEXT vs electron's INTEGER).

## 6. If B: which lines change and the new formula

The new canonical formula (already in shared, mobile uses it):

```ts
// packages/shared/src/lib/stringToNumberID.ts — keep as-is.
// packages/shared/src/indexing/chunk-id.ts (NEW, extracted):
export function chunkIdFor(bookId: string, chunkText: string): string {
  return stringToNumberID(`${bookId}|${chunkText}`).toString()
}
```

Changes required on electron:

1. **`packages/shared/src/indexing/index-program.ts:81-82`** — replace the
   positional `chunkId(pageNumber, bookId, index)` export with (or
   alongside, behind a feature flag during migration) `chunkIdFor(bookId,
   chunkText)`. Update `processPage` at L102-107 to call the new function
   with `(String(deps.bookId), data)`.
2. **`packages/shared/src/indexing/index-program.test.ts:22-27`** — replace
   positional assertions with content-hash assertions.
3. **`apps/rishi-electron/src/main/database/schema.ts`** (chunk_data table)
   — keep `id` as INTEGER if we agree on `parseInt(stringToNumberID(...))`,
   OR migrate to TEXT to match mobile. Recommendation: keep INTEGER but
   accept the numeric form (drop `.toString()` only at the boundary).
4. **Electron migration** — on first launch after the change, re-run
   `indexBookProgram` for every book whose chunk_data was minted with the
   old formula. Detection: schema version bump, or per-book `id_formula`
   column.
5. **Mobile `chunker.ts:72-74`** — replace local `chunkIdFor` with the
   import from `@rishi/shared/indexing/chunk-id` so there is exactly one
   source of truth.
6. **`apps/mobile/lib/book-import/adapters.ts:415-420`** — the sentinel
   `id: idx` is fine since it never reaches a DB row; no change needed.

## 7. Test plan: shape of `chunk-id-parity.test.ts`

**Location:** `packages/shared/__tests__/chunk-id-parity.test.ts` (new)
— or, if we prefer to colocate, `packages/shared/src/indexing/
chunk-id-parity.test.ts`. The shared package is the canonical home because
both electron and mobile import from it.

**Fixture:** `packages/shared/src/formats/__fixtures__/test-book.epub`
(already exists, already used by shared's `formats` tests, available to both
electron and mobile via `@rishi/shared`).

**Assertions:**

```ts
import { describe, it, expect } from 'vitest'
import { extractEpubText } from '@rishi/shared/formats/epub' // or shared equivalent
import { chunkText } from '@rishi/shared/rag/chunker' // shared once extracted
import { chunkIdFor } from '@rishi/shared/indexing/chunk-id' // post-extraction

describe('chunk-id parity (shared = mobile = electron)', () => {
  const bookId = 'fixture-book-1'
  const fixturePath = require.resolve(
    '@rishi/shared/formats/__fixtures__/test-book.epub'
  )

  it('produces the same chunk IDs for the same input across two runs', async () => {
    const sectionsA = await extractEpubText(fixturePath)
    const sectionsB = await extractEpubText(fixturePath)
    const chunksA = chunkText(sectionsA).map((c) => chunkIdFor(bookId, c.text))
    const chunksB = chunkText(sectionsB).map((c) => chunkIdFor(bookId, c.text))
    expect(chunksA).toEqual(chunksB)
  })

  it('different bookIds produce disjoint id sets for identical text', () => {
    const text = 'The quick brown fox jumps over the lazy dog.'
    expect(chunkIdFor('book-A', text)).not.toBe(chunkIdFor('book-B', text))
  })

  it('matches the snapshot for a known input (regression guard)', () => {
    expect(chunkIdFor('book-1', 'hello world')).toMatchInlineSnapshot()
  })

  it('mobile chunkIdFor === shared chunkIdFor (no drift)', async () => {
    // Once shared owns chunkIdFor, the mobile chunker imports it directly,
    // so this is a compile-time guarantee. Until then, assert byte-equality
    // by importing both:
    const { chunkIdFor: sharedFn } = await import('@rishi/shared/indexing/chunk-id')
    const { chunkIdFor: mobileFn } = await import('../../apps/mobile/lib/rag/chunker') // private import OK for test
    expect(sharedFn('b', 't')).toBe(mobileFn('b', 't'))
  })

  it('REGRESSION: electron index-program produces the SAME id as shared chunkIdFor (post-migration)', () => {
    // After B, the positional chunkId formula is gone or wraps chunkIdFor.
    // Pre-migration this test is RED and pins the divergence.
    const { chunkId } = require('@rishi/shared/indexing/index-program')
    // Post-B: chunkId(pageNumber, bookId, index, text) -> chunkIdFor(String(bookId), text)
    expect(chunkId(1, 7, 0, 'hello world')).toBe(chunkIdFor('7', 'hello world'))
  })
})
```

The final test is the **parity gate** that drives the verdict-B migration:
it is RED today (proves divergence), GREEN once electron adopts the shared
formula. Land it RED in T-P0.2 as the failing-test phase, then green it in
T-P0.3 (electron-side migration).
