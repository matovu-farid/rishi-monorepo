## Bug Summary
`service.test.ts` L289-300 asserts cancellation via
`expect(events).toContainEqual({ kind: 'complete', cancelled: true })`.
`toContainEqual` permits the array to ALSO contain a
`{ kind: 'complete', cancelled: false }` (e.g. a stray completion event
fired by the still-active scanner after cancellation). The single-flight
guard at L277-287 makes this exact race plausible: if scanner.emit
delivers a queued `scan-complete` after the local cancellation flag
flips, the service would emit BOTH events and the test would still pass.
The cancel contract should be exact, not "at least contains".

## Reproduction
- Test file: `apps/rishi-electron/src/renderer/src/services/book-import/service.test.ts` lines `289-300`
- Failing assertion (tightened): change to
  `expect(events.filter(e => e.kind === 'complete')).toEqual([{ kind: 'complete', cancelled: true }])`
  — and add `scanner.emit({ kind: 'complete' })` AFTER the
  `cancelDiscovery()` await to prove the listener was actually unbound.
- How to run: `pnpm --filter rishi-electron test src/renderer/src/services/book-import/service.test.ts -t "cancelDiscovery propagates"`

## Tester Analysis
`toContainEqual` is `practices-audit.md`-grade weak matching whenever the
asserted invariant is "exactly one of these events, with this content".
Discovery completion is exactly such a single-shot contract — UI badges
and refresh logic key off it. A duplicate or contradictory complete
event downstream is a real-world bug class for scanners (well-known in
Electron IPC listeners), and the current test cannot detect it.

**Reasoning:** `service.test.ts:299` uses `toContainEqual({ kind: 'complete', cancelled: true })`, which only asserts presence — it would still pass if the array also contains `{ kind: 'complete', cancelled: false }`.
