## Bug Summary
The happy-path test in `service.test.ts` (L112-135) waits for `upload-started`
by sleeping `setTimeout(r, 0)` AFTER `importFromPath` resolves. That is a
classic unawaited-promise smell: a production user calling `await
service.importFromPath(...)` reasonably expects the lifecycle events for
that import to have fired by the time the promise settles, but the test
proves they have not — `upload-started` only lands on the next macrotask.
Either (a) the contract is "upload-started is fire-and-forget after the
return" and the test should not assert it in the same ordered array, or
(b) the implementation has a stray un-awaited promise that should be
joined before resolving. Today's test silently encodes (a) while reading
like (b), which is a contract bug.

## Reproduction
- Test file: `apps/rishi-electron/src/renderer/src/services/book-import/service.test.ts` lines `112-135`
- Failing assertion (after removing the `setTimeout(0)` wait):
  `expect(events.map((e) => e.kind)).toEqual(['copying','parsing','saving','done','upload-started'])`
  will fail — `upload-started` is missing because `importFromPath` resolved
  before the upload-kickoff microtask flushed.
- How to run: `pnpm --filter rishi-electron test src/renderer/src/services/book-import/service.test.ts -t "returns ok and emits copying"`

## Tester Analysis
The orchestrator kicks off the file-sync upload after `done` but does not
await it (otherwise no `setTimeout(0)` would be needed). If the intent is
"upload is best-effort, don't block the caller", the public contract
should expose a separate awaitable (e.g. `service.uploadsInFlight()` or
an `upload-complete` event) so callers/tests can synchronise without
sleeping. As written, the sleep is a flake magnet on slow CI and the
ordered-array assertion is testing implementation timing rather than
behavior.

**Agent type:** team-reviewer
**Flake check:** N/A (not classified as BUG)
**Reasoning:** Production code in `importer.ts` L44-47 and L165-169 explicitly documents the fire-and-forget contract: the upload "Runs asynchronously (microtask), so `done` lands in the event stream before `upload-started`." `runUpload` (L49-77) deliberately wraps the emit + upload in `setTimeout(..., 0)` precisely so `await importFromPath(...)` resolves before `upload-started` lands. T7's note is correct — this is intentional design, not an un-awaited promise leak. The companion test in `importer.test.ts` L205-227 codifies the same ordering (`done` before `upload-failed`, `kinds).toContain('upload-started')` without an ordered-array assertion). However, the happy-path test in `service.test.ts` L113-134 still over-specifies by lumping `upload-started` into the exact ordered array after a `setTimeout(0)` flush — that asserts implementation timing (one macrotask hop) rather than the contract (upload events arrive eventually, after `done`). If `runUpload` ever switches from `setTimeout(0)` to a `queueMicrotask`/`Promise.resolve().then(...)` or a longer delay, this test breaks for no behavioral reason. Not a production bug; test asserts implementation timing.
**Suggested fix scope (if A or B):** Drop `upload-started` from the ordered-array assertion and instead assert `events.slice(0,4)` equals `['copying','parsing','saving','done']` and separately `await vi.waitFor(() => expect(events.map(e=>e.kind)).toContain('upload-started'))`, mirroring the importer.test.ts style.
