## Bug Summary
`tutorialStore.test.ts` "should not start tour if completed" (L22-26)
seeds `tourCompleted: true` via raw `setState` and then calls
`startTour()`. The test passes because production `startTour()` short-
circuits on `get().tourCompleted` (L102-105). However, the real-world
"already completed" gate is driven by the module-load-time read of
`localStorage.getItem(TOUR_COMPLETED_KEY) === '1'` at production
L95-98, which runs exactly once when the store module is first
imported. The test fixture never re-exercises that init path: every
test in the file reuses the singleton store instance imported at L2,
so a regression where the init-time gate is broken (e.g. wrong key
string, JSON-parse instead of `=== '1'`, init reads from
`sessionStorage`) will pass.

## Tester Analysis
Two related coverage issues compound here:

1. **Module-singleton init path uncovered.** The `tourCompleted`
   initial value is computed at module-load (production L95-98)
   from `localStorage`. None of the tests in the file pre-seed
   localStorage *before* the store module loads — the import on
   L2 already evaluated the init, and `vi.resetModules()` is never
   called. Compare with prefsStore.test.ts (L13 `vi.resetModules()`
   + dynamic `await import(...)` per test) which DOES re-init.
2. **Persisted-state contract is implicit.** No test pins the
   storage-key string (`'rishi:tour-completed'`) or the marshal
   format (`'1'`). The skip-tour test at L41-45 happens to assert
   the key+value, so there is partial coverage, but no test
   asserts the init path reads the same key+format.

Suggested approach: mirror prefsStore.test.ts's dynamic-import
pattern for one targeted test ("when localStorage has
`rishi:tour-completed=1` at module load, `startTour()` is a no-op
without seeding `tourCompleted` via setState"). This also
documents the persistence contract end-to-end.
