## Bug Summary
`makeDb` exposes `failOn: 'savePageDataMany' | 'saveVectors'` (L13, L24,
L30) but NO test in `indexer.test.ts` exercises either rejection path.
Production-side, `indexer.ts:64` (`await deps.db.savePageDataMany(...)`)
is OUTSIDE the try/catch that swallows embed/vector errors (L71-88), so
a `savePageDataMany` rejection propagates unhandled out of `indexBook`.
Conversely `saveVectors` (L82) IS inside the try/catch — and the
emitted `indexed.ok` flag depends on which call threw. The current test
suite cannot distinguish these two behaviors, so a regression that moves
the try/catch boundary (e.g. wrapping chunk save too, or unwrapping the
vector save) would be undetectable.

  - For `failOn: 'saveVectors'`: expect `events.find(e => e.kind==='indexed')` equals
    `{ kind: 'indexed', bookId: 42, ok: false }` AND `savePageDataCalls.length === 2`.

## Tester Analysis
`indexer.ts:69` comment "Best-effort: swallow failures so page data
stays" makes the partial-failure (chunks saved, vectors failed) case a
named contract — yet that exact path has zero coverage. Combined with
the wired-but-unused `failOn` paths in `makeDb`, this is a coverage gap
hiding a real behavioral split. Two tests, both with the helper already
in place.
