## Tester 1 (warm-restore slice — pdf-warm-restore.spec.ts + pdfStore.test.ts)

- **PDF warm-restore e2e is `test.skip(...)`** — `apps/rishi-electron/e2e/pdf-warm-restore.spec.ts:33`. Skip rationale ("Phase 3 window split") is plausible: the test asserts `app.page.locator('canvas.react-pdf__Page__canvas')` on the library window, but per Phase-3 `openBook` now returns the new book window (`e2e/helpers/electron-app.ts:206-225`), so the canvas would never be on `app.page`. Either (a) un-skip and migrate to use the returned `bookPage` like `pdf-persistence.spec.ts:21` does, or (b) link a follow-up ticket. Currently the skipped suite leaves the PDF warm-restore LRU contract (`src/renderer/src/services/reader-cache/pdf-cache.ts`) entirely unexercised at e2e.
- **PDF cache diagnostic surface is exposed but never asserted on.** `pdf-cache.ts:23-32` mirrors `epub-cache.ts` by exposing `window.__readerCache.pdf.{has,size,stats,resetStats}`, but no spec consumes any of them — `git grep "__readerCache.pdf"` yields zero hits in `apps/rishi-electron/e2e/`. The EPUB equivalent at `epub-warm-restore.spec.ts:94-95,109-111` asserts `stats.hits>0 && stats.misses===0`. PDF has the production surface and the LRU machinery; the corresponding e2e assertion is missing.
- **PDF in-window reopen / "warm cache hit" is no longer covered by ANY spec.** The skipped warm-restore was the only test that exercised reopen-within-session against the LRU. `pdf-persistence.spec.ts` covers location restoration *across a closeBook+openBook cycle* (a different code path: `books.location` SQLite column), not the cache. So the PDF cache LRU has only unit-level coverage (`reader-cache/cache.test.ts`); it is untested at the integration level.
- **No reopen/restore test in `pdfStore.test.ts`.** The unit suite covers reducer math (nextPage, previousPage, dual-page, paragraph reset) but never asserts state transitions across a simulated mount/unmount/restore — e.g., that `pageNumber` correctly seeds from a persisted location string. The companion warm-restore concept is wholly absent here, despite the pilot scope pairing this file with `pdf-warm-restore.spec.ts`.
- **`pdfStore`'s scroll→page subscription side-effect (L201-208) has no unit test.** This is precisely the code path that participates in restore (a persisted page index would land via `setPageNumber`, while in-flight scroll updates land via `setScrollPageNumber`; the gating on `BookNavigationState.Navigating` is what prevents a stale scroll from clobbering the restored page). No test exercises it. EPUB store has an analogous subscription (`epubStore.ts:174-207`) that is also unit-uncovered.
- **`pdfStore.test.ts` `resetParagraphState` test asserts 3 of 5 reset fields.** Reducer at `pdfStore.ts:166-173` resets `{isDualPage, pageCount, highlightedParagraphIndex, isHighlighting, isRenderedPageState}`. Test at `pdfStore.test.ts:106-112` only checks the first three. Coverage gap on the same reset contract.

## Tester 2 (epub-warm-restore + epubStore unit)

- **EPUB has no live `pdf-persistence.spec.ts` equivalent.** PDF has `e2e/pdf-persistence.spec.ts` exercising page-index restore across close+reopen via `books:updateLocation`. EPUB has *no* live counterpart that exercises `currentEpubLocation` (CFI) being persisted to SQLite and restored on cold reopen. `e2e/epub-warm-restore.spec.ts:69` is `test.skip(...)` AND only covers the LRU cache path, not the DB-backed location restore. Suggested new spec: `e2e/epub-persistence.spec.ts` — import EPUB, open book, navigate to a known CFI, close window, reopen, assert `currentEpubLocation` equals the saved CFI (file paths exercised: `src/main/ipc/books.ts:65` `books:updateLocation`, `src/renderer/src/stores/epubStore.ts:71` `setCurrentEpubLocation`).
- **`epubStore.test.ts` has no restore-cycle assertion.** The unit test (`src/renderer/src/stores/epubStore.test.ts:1-137`) exercises set/get parity for `currentEpubLocation`, `bookId`, `theme`, but never simulates the warm-restore flow: set location -> unmount -> remount (new `bookId` via `setBookId`) -> assert the location is wired up correctly. There is no unit-level assertion that re-mounting the same `bookId` reuses the persisted location, nor that mounting a *different* `bookId` does NOT inherit a stale location. (Production code path: `routes/books.$id.lazy.tsx:55` calls `reset()` on unmount, but the test doesn't guard that contract.)
- **No EPUB cache cold-miss assertion.** `epub-warm-restore.spec.ts:94` asserts the cache `has(bookId)` after first open, but no test asserts `stats.misses > 0 && stats.hits === 0` on a *cold* first open — i.e., that the first open is genuinely cold and not silently hitting a leftover entry. Without this, a false-positive "warm" assertion could pass on a misconfigured cache. The renderer-side diagnostic exposes `resetStats`/`stats` for exactly this (`src/renderer/src/services/reader-cache/epub-cache.ts:37-42`); the cold-side of the assertion is not used.
- **EPUB `setBookOutline` / `bookOutline` field is uncovered at unit level.** `epubStore.ts:44, 70, 226, 237-248` introduces an outline field, a setter, an auto-clear-on-blanked-bookId via subscription, and a subscription that triggers `getVoiceChatService().preconnect(...)`. `epubStore.test.ts` exercises none of these. Critically, `reset()` (lines 74-91) does NOT include `bookOutline` in its reset set — the implementation relies on the `bookId -> ''` subscription side effect (`epubStore.ts:218-230`) to clear it. There is no unit test that pins this indirection, so a future refactor that removes `initEpubSubscriptions()` from a code path would silently leak the prior book's outline into the next book's state.
- **No close-of-book-window cache eviction assertion (Phase 3).** Per the skip comment at `epub-warm-restore.spec.ts:69-74`, Phase-3 (per-window) lifecycle changes the warm-restore surface — closing a book window destroys its renderer. There is no spec asserting that the parent (library) window's `__readerCache.epub` either retains or correctly evicts an entry after the book window is closed. Until this lifecycle question is pinned by a test, the cache contract under Phase-3 is undefined behavior. (Production code paths: `epub-cache.ts:26-29`; close-window flow discoverable from `e2e/helpers/electron-app.ts:closeApp`.)

## Tester 4 (MOBI slice — mobi.spec.ts + formats-mobi.test.ts)

- **No `mobi-real-import-routing.spec.ts` counterpart to AZW3.** `e2e/azw3-real-import-routing.spec.ts` was written specifically to catch dispatch-bypass regressions (`.azw3` ending up as `kind: 'mobi'`). `mobi.spec.ts:29-33` uses the `importBook` helper that hardcodes `kind: 'mobi'` (`e2e/helpers/electron-app.ts:113-122`), bypassing `dispatchFormatExtraction` (`src/renderer/src/services/book-import/dispatch.ts:43-56`). For MOBI this happens to match the production path's output (extension `.mobi` -> `getMobiData` -> `extractKindleData(filePath, 'mobi')` -> `kind: 'mobi'`, formats.ts:626-628), so production is currently fine — but the test cannot catch a future regression where the renderer dispatcher mis-routes `.mobi`. A `mobi-real-import-routing.spec.ts` using `importBookViaOpenFile` (`e2e/helpers/electron-app.ts:138-178`) would restore parity with AZW3.
- **No MOBI warm-restore / chapter-index restore test.** MOBI persists location as `<chapter>:<page>` (Azw3View handles MOBI too, see `routes/books.$id.lazy.tsx:83`) but no e2e or unit test asserts that closing+reopening a MOBI book restores `chapterIndex`. PDF has `pdf-persistence.spec.ts` for this; MOBI/AZW3 have nothing. The Azw3View location parser at `Azw3View.tsx:50-52` (`parseLocation(book.location)`) is exercised by no test.
- **`formats-mobi.test.ts` is parse-only and never exercises the IPC handlers.** The suite at `src/main/ipc/__tests__/formats-mobi.test.ts:1-277` calls `stripHtmlTags`, `parseMobiMetadata`, `parseMobiChapters` directly. The IPC entry points `formats:getMobiData`, `formats:getMobiChapter`, `formats:getMobiChapterCount`, `formats:getMobiText` (`src/main/ipc/formats.ts:705-744`) and the dispatch wrapper `extractKindleData` (`formats.ts:576-624`) — including the AZW3-vs-MOBI fork at L586-606 — are not exercised. A wrong-extension routing or error-wrapping regression inside the handlers would slip through.
- **No AZW3 unit counterpart to `formats-mobi.test.ts`.** `src/main/ipc/__tests__/` contains only `formats-mobi.test.ts` and `auth.test.ts`. AZW3 has zero unit-level coverage of either `extractAzw3Data` or the `formats:getAzw3Data` handler (formats.ts:630-632, 714-720). The pair is unbalanced and the AZW3-only `try/catch` fallback path at `formats.ts:586-598` (swallows EXTH-parse errors for KF8) is untested.
- **`formats-mobi.test.ts` uses a synthetic in-memory MOBI buffer, never the real fixture on disk.** `buildMobiBuffer` (`formats-mobi.test.ts:13-150`) constructs a 137-line minimal PDB+MOBI buffer. The real fixture `e2e/fixtures/test-book.mobi` (780 KB) is loaded only by `components/azw3/parser.mobi.test.ts:11`. The synthetic buffer can diverge from real-world MOBI files (compressed records, trailer bytes, multibyte flags); a parser regression on real files would pass the synthetic-buffer suite.
- **MobiView is dead code (`routes/books.$id.lazy.tsx:10-12,83`) but no test asserts the routing.** `books.$id.lazy.tsx:83` renders `Azw3View` for both `kind: 'mobi'` and `kind: 'azw3'`. A regression that re-wires `MobiView` for `kind: 'mobi'` would not be caught — `mobi.spec.ts:36-40` does not assert the iframe shape distinguishes Azw3View (`src=blob:`) from MobiView (`srcDoc`) the way `azw3-real-import-routing.spec.ts:36-41` does. Parity-with-AZW3 gap.

## Tester 3 (azw3-real-import-routing.spec.ts — pilot label is import-routing, not warm-restore)

- **PG-013-A — No AZW3 warm-restore spec exists (scope mismatch with pilot label).** `azw3-real-import-routing.spec.ts` is listed under the pilot's warm-restore-relevant slice, but it never closes the app or reopens the book. It opens the book once in-session and asserts only the `<iframe>` shape (`apps/rishi-electron/e2e/azw3-real-import-routing.spec.ts:34-41`). PDF has both LRU-cache (skipped) and location-restore (`pdf-persistence.spec.ts`) angles; AZW3 has neither. AZW3's persisted location is `<chapter>:<page>` (parsed at `apps/rishi-electron/src/renderer/src/components/azw3/Azw3View.tsx:50-53`); no test verifies it survives close+reopen. Suggested new spec: `e2e/azw3-warm-restore.spec.ts` — `importBookViaOpenFile(AZW3_FIXTURE)`, `openBook`, navigate to a known `chapter:page`, close, relaunch, reopen, assert `book.location` round-trips and `Azw3View` mounts at the saved position. (Tester 4 raised the equivalent for MOBI at row 27 above — both formats need the same companion spec.)
- **PG-014-A — No AZW3 unit counterpart for extractor/IPC.** MOBI has `apps/rishi-electron/src/main/ipc/__tests__/formats-mobi.test.ts` (parse-only). AZW3 has nothing. The AZW3-specific branch at `apps/rishi-electron/src/main/ipc/formats.ts:586-598` (the "swallow parse errors and fall back to filename-derived metadata" path that distinguishes AZW3 from MOBI) is unexercised by unit tests; only e2e hits it implicitly. Suggested test: build a truncated PalmDOC header so `parseMobiMetadata` throws inside `extractKindleData(buf, 'azw3')`, assert the result still returns `{ kind: 'azw3', title: <basename>, coverKind: 'fallback' }`; mirror with the negative case for `'mobi'` (must throw, per doc-comment at `formats.ts:572-574`). This overlaps with Tester 4's row 29; tracked here as the AZW3-side of the symmetry.
- **PG-015-A — Cold-start `open-file` path (`pendingOpenFiles` drain) is uncovered for every format.** `importBookViaOpenFile` (`e2e/helpers/electron-app.ts:138-178`) emits the synthetic `app.emit('open-file', ...)` *after* `launchApp` has settled the renderer, so it always hits the live-renderer branch of `deliverOpenFiles` (`apps/rishi-electron/src/main/index.ts:36-42`). The buffered branch (`pendingOpenFiles.push(...)` at line 41, drained via the `did-finish-load` hook at line 150-155 and via `files:getPending` in `useFileOpenHandler.ts:52-55`) — the actual path for "double-click a .azw3 in Finder with the app not running" — has zero spec coverage. AZW3's spec is closest in shape because the original AZW3 routing bug only repro'd via the real OS pipeline; a regression in `getPendingOpenFiles` IPC wiring would be invisible. Same symmetric gap across PDF/EPUB/MOBI/AZW3.
- **PG-016-A — `iframe` shape assertions no longer distinguish AZW3 from MOBI routing.** At `azw3-real-import-routing.spec.ts:36-41` the spec asserts `src` matches `^blob:` and `srcdoc === null` to "confirm Azw3View, not MobiView". But per `apps/rishi-electron/src/renderer/src/routes/books.$id.lazy.tsx:83`, both `kind === 'mobi'` and `kind === 'azw3'` now dispatch to `Azw3View` — the legacy `MobiView` is dead code (comment at `books.$id.lazy.tsx:10-12`). So even if a future regression made AZW3 import with `kind: 'mobi'`, the iframe assertions would still pass (Azw3View renders the same shape regardless of `book.kind`). Only the `getBookKind` DB assertion at line 29 actually pins the bug-fix contract. Recommendation: either drop the iframe-shape block as misleading, or strengthen it to a content-level assertion (e.g. iframe-frame text contains a known phrase from the fixture's first chapter) so the test's intent — that the *user-visible* reader is the AZW3 one — survives MobiView's removal. Cross-ref: same issue affects MOBI's missing iframe assertion (Tester 4 row 31).
