## Bug Summary
`indexer.test.ts` L99 asserts `expect(savePageDataCalls).toHaveLength(2)`
but never inspects the contents of the saved rows. The indexer at
`indexer.ts:58-64` synthesises `ChunkDataInsertable` rows from `pageData`
by re-mapping `{id, pageNumber, bookId, data}`. A regression that swapped
`p.bookId` for the loop variable, dropped `pageNumber`, or sent
`pageData` for the wrong book would still produce a length-2 array and
pass the test. The full-pipeline test is the only place the chunk-save
contract is exercised; weak matcher here means the contract is unpinned.

## Reproduction
- Test file: `apps/rishi-electron/src/renderer/src/services/book-import/indexer.test.ts` lines `88-108`
- Failing assertion (strengthened): replace L99 with
  `expect(savePageDataCalls).toEqual(samplePageData)` and the test still
  passes today — but a `bookId: 0` swap in `indexer.ts:58-64` would no
  longer be caught.
- How to run: `pnpm --filter rishi-electron test src/renderer/src/services/book-import/indexer.test.ts -t "saves chunks, embeds in batches"`

## Tester Analysis
This is a `practices-audit.md` candidate (weak assertion / count theater)
that protects a high-risk path: silently writing wrong chunk metadata
would corrupt RAG lookup without surfacing an error. The fix is a
one-line strengthening to `.toEqual(...)` or `.toMatchObject([...])`
asserting `bookId`, `pageNumber`, and `data` on every saved row.
