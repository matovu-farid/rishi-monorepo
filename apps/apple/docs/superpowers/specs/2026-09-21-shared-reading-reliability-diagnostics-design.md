# Shared Reading Reliability and Development Diagnostics Design

**Status:** Approved for planning

## Goal

Finish the shared-reading production work without making end-to-end testing a
delivery gate: reliable authority handling, reconnect/rejoin recovery,
account-lifecycle cleanup, deletion revocation, migration safety, actionable
Worker errors, and privacy-safe development diagnostics.

## Scope

The Apple app must reject stale shared-reading events using separate typed room,
roster, controller, and connection generations. A reconnect must use one
cancellable state machine that classifies retry, bearer refresh, admission
refresh, and terminal failures. Rejoining an active session must remain visibly
reconnecting until a fresh matching server state, roster, and progress snapshot
arrive. A single composition-root registry owns every account-scoped session and
drains it before sign-out, account switch, or deletion can publish new identity
state.

The Worker must return a consistent, user-safe error envelope containing a
stable error code, retryability, recommended action, and opaque correlation ID.
Detailed Worker diagnostics remain in Worker Logs. Account deletion must revoke
room references idempotently before related D1 state is finalized. Session-invite
migration reconciliation is chosen only after a read-only production D1 audit;
all resulting migration artifacts are generated by Drizzle.

## Development diagnostics

Diagnostics are DEBUG-only and local to each Apple target. The existing
`SimulatorDumpSink` remains the one logging mechanism: it writes non-blocking
NDJSON files in each app container for iPhone Simulator and Mac Catalyst. A
host-side collector accepts explicit target identifiers and one explicit output
path, labels each event by source, and emits a merged NDJSON file plus a small
manifest. It never guesses a target or automatically exports data.

Every shared-reading boundary emits an allowlisted structured event: create,
redeem, local-book validation, admission, socket lifecycle, reconnect decision,
event acceptance/rejection, rejoin readiness, leave/end, lifecycle drain, and
error. The common fields are timestamp, source, event name, opaque correlation
ID, hashed/truncated session debug ID, outcome, error code, authority
generations, reconnect attempt, and duration when applicable.

Logs must never contain bearer tokens, admission tickets, invite URLs/tokens,
email addresses, raw user IDs, book metadata/content/hashes/positions, SDP/ICE
payloads, or raw error bodies. Logging failures are non-fatal and must not block
actors or WebSocket handling. The DEBUG local files are not telemetry and are
not uploaded automatically.

## Error contract

All externally visible shared-reading failures use the existing semantic error
concepts extended as needed, serialized as an allowlisted envelope:

```json
{
  "code": "SIGNALING_DEGRADED",
  "retryable": true,
  "action": "retry",
  "correlationId": "opaque-id"
}
```

Messages remain safe for display. The Worker logs the causal category and
correlation ID but not credentials or personally identifying payloads. The
client includes the correlation ID in its local diagnostic events so a developer
can correlate a user-facing failure with Worker Logs.

## Out of scope

- A shared writable filesystem across the app targets and Workers.
- Production telemetry, diagnostics upload, or persistent end-user logging.
- Making E2E acceptance a prerequisite for this implementation.
- Hand-authored migration SQL or modification/removal of historical migrations.
- Electron changes.

## Acceptance criteria

1. Stale/mixed authority events cannot overwrite current shared-reading state.
2. Reconnect/rejoin reaches a defined terminal or authoritative state with no
   duplicate reconnect task.
3. Sign-out, account switch, deletion, and late old-account callbacks cannot
   retain or publish an old shared-reading session.
4. Worker errors are actionable and correlated without exposing sensitive data.
5. Developers can explicitly merge Catalyst and iPhone DEBUG local diagnostic
   files after a test run.
6. Production migration handling is selected from read-only database evidence
   and only generated Drizzle artifacts are applied.
